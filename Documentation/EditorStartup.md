# Editor Startup Presentation

`EditorFramework/GUI/EditorSplashScreen` is a lightweight Qt Widgets startup panel. It uses the existing XII wordmark, converted from the repository's Colonna MT logo artwork into SVG paths so Linux and macOS do not need that font installed. System UI fonts provide native typography; Qt paints text, vectors, and a standard progress bar at the current device pixel ratio. No GPU context, image generator, animation framework, downloaded asset, or extra runtime dependency is involved.

The panel uses a black background, white branding and primary text, and neutral gray secondary text in both light and dark desktops. Blue is limited to the progress fill and small top accent. Translucent white frame lines, separators, and the progress track blend over the black background; the existing SVG wordmark retains its transparent background. The window remains opaque for consistent contrast and platform behavior. Its logical composition is 720 × 412, scaled down to fit small available screen geometries. It starts on the screen under the pointer, with the primary screen as fallback. Window flags identify it as a splash, request no focus, and omit always-on-top behavior; `WA_QuitOnClose` is disabled. It borrows the editor solely for dialog ownership, without establishing a native transient parent, creating the editor's native handle, or raising itself above an already-visible editor. It does not create or replace a taskbar window. The application title, SDK version, build configuration/platform/bitness, and existing CMake-generated revision identify the executable being started.

## Actual Startup Stages

The existing `StartupEditor` sequence and project-selection precedence remain authoritative. Stage calls are adjacent to the work they describe:

- Prepare the workspace and initialize editor subsystems, document types, actions, and asset services.
- Prepare application/user directories and load preferences, shortcuts, tool settings, and recent projects.
- Create existing Editor panels and discover plugin bundle metadata.
- Open/create the explicit or recent project, load its plugin DLLs and configuration, register asset types, initialize the existing rendering process, and index assets.
- Restore project documents and transition to the Editor, project dashboard, or an existing startup dialog.

There is no overall startup percentage or minimum display duration. Most stages have unknown cost and use Qt's indeterminate progress mode. The resolved plugin load order has a real item count; only that stage displays measured completed/total work. Counts represent items, not elapsed time. Advancing to another stage restores indeterminate mode. The existing general `xiiProgress` dialog is attached only after startup completes, including when `-NoSplash` is used, avoiding competing startup windows; taskbar/tray subscriptions retain their existing sources.

## Single Window Transition

`StartupEditor` constructs the main container with window presentation disabled. The container's `setVisible` override rejects direct, indirect, and queued show requests before native mapping. Container and document layout scheduling defer work during this phase; tab selection does not raise application windows, and shared tray/notification activation cannot bypass startup. Project opening does not dismiss the splash on its normal completion path.

At the end of initialization, the existing container geometry/dock state and document layouts are restored while hidden. Layout restoration no longer implicitly calls `show` or `showMaximized`; the saved state, or the default maximized state, is applied without mapping the window. The general progress dialog remains detached during this work. Startup then closes the splash, enables presentation, and invokes the existing Editor activation path exactly once, without event pumping between these steps. A pending quit skips restoration/reveal and does not overwrite layouts with an uninitialized workspace.

The vendored ADS integration reuses its existing pending-floating list to defer floating-window presentation while the owning window is hidden, including floating windows created by state restoration. Entries are removed when their Qt-owned windows are destroyed. Showing the completed workspace releases those windows without activation; the Linux ADS activation paths respect hidden owners and `WA_ShowWithoutActivating`. This corrects the dock library's underlying show path rather than hiding already-mapped windows or covering them with the splash.

## Responsiveness and Ownership

Initialization stays on its existing GUI thread and in its existing order. Painting a status never implicitly processes arbitrary commands. Qt events are serviced at the initial expose and between plugin operations, after each prior operation has returned. The render-process startup wait listens to actual IPC/channel and child-process events; the asset-index wait uses an empty dependent task group and its completion callback to wake a stack-owned Qt event loop. Neither adds polling, artificial sleeps, or another startup scheduler. Editing input is excluded from these nested waits, which also preserve the original unbounded wait contract until response, disconnection, or a startup quit request.

Individual synchronous subsystem/plugin callbacks, process launch, and final asset metadata work still run synchronously. They must return before another Qt event boundary; moving these operations to worker threads would require a separate thread-safety change and is outside this presentation feature.

UI service ticks remain enabled during the interactive rendering-process wait, but redraw synchronization is gated by the connection's existing engine-setup state. No redraw message or blocking redraw acknowledgement wait runs until the setup/project-ready handshake completes. This also applies while restarting the engine, after shutdown, and after failed setup; normal synchronization resumes once the engine is configured.

Only GUI-thread code owns or paints the splash. IPC I/O callbacks enqueue receiver-bound invocations; synchronized subscription teardown precedes destruction of the local event loop. Asset initialization is joined before its task-dependent loop is destroyed. No borrowed worker-owned text or QWidget is accessed from another thread.

The splash is closed immediately at the end of startup, before dashboard selection, and at shutdown. It does not use `QSplashScreen::finish`'s expose wait. Normal initialization shows only the splash. Required project questions/failure dialogs remain actionable and temporarily hide the splash, while the editor stays hidden; completing the dialog resumes a live splash until initialization finishes. A user-dismissed splash stays dismissed. Optional version-check UI waits for the existing post-startup idle event. If a platform still selects the splash as an implicit dialog parent, the dialog's polish event transfers that parent to the borrowed editor only if it is already visible, or uses no parent, preserving its flags without activating a hidden owner. An actual rendering-process startup failure during interactive startup directs the user to the Editor log. Click-to-dismiss hides presentation while initialization continues.

Native close/quit requests received during startup are recorded once. An IPC startup wait wakes and returns through its normal process cleanup path. Already running asset initialization is joined before teardown. Once the initialization scope returns, `RunEditor` skips `exec` for a pending quit and ordinary `ShutdownEditor` owns cleanup. Startup never destroys partially initialized documents/plugins from a nested event loop. A fresh startup resets that request.

The `-NoSplash` option and existing `EditorPreferences/ShowSplashScreen` setting remain honored. Headless, background, and normal unit-test startup do not create a splash. Safe mode, explicit `-project`/`-newproject`, document arguments, recent-project policy, and the existing project-switch process behavior retain their established meanings.

## Verification and Acceptance

The `EditorSplash` suite renders the actual production widget under light/dark application palettes at 1×, 1.5×, 2×, and 3× image device pixel ratios. PNGs are written under the test output's `SplashPreviews` directory for visual inspection. It also covers actual versus unknown work, count bounds, full accessible Unicode details, taskbar/focus flags, available-screen placement, dismissal/modal diagnostic handoff, suppression options, startup/shutdown with a quit before the main event loop, real pipe/protocol connection and project-ready response delivery, child-process disconnection, and a quit during an event-driven IPC wait. Run the suite twice with the same output directory to exercise fresh processes before and after saving the real startup shortcut assignments; the Editor's plugin lifecycle is not designed for repeated `StartupEditor` calls in one process. The shortcut fixture and splash-policy settings are isolated from the user's preferences.

Regression suites are `EditorJumpList` (including startup actions), `EditorTaskbar`, `EditorSystemTray`, `EditorNotifications`, and `CodeGen`. The implementation uses existing Qt Widgets/SVG dependencies; the test target explicitly links Qt Svg for the public widget header.

`EditorInteractiveProjectStartup` uses actual interactive startup flags, rather than the unit-test wait path. Its first run prepares and opens an existing empty project in isolated preferences; a second fresh process with the same output directory restores that project from recent history without project arguments. It forces an end-frame tick before setup, rejects premature redraw synchronization warnings, checks real engine readiness and subsequent redraw acknowledgements, and retains the hidden-workspace/single-reveal assertions. Optional asset-transformation questions are declined through the existing dialog during the test. Run this group separately from other complete Editor lifecycle tests.

`EditorStartupVisibility` covers queued show/layout requests, hidden floating-dock restoration and destruction, and an actual Editor startup with saved maximized geometry and a floating tool. Show/activation observers reject application-window presentation during initialization and verify one container show after completion. Run it in fresh processes with the same output directory for cold/warm preferences. `EditorStartupFailureVisibility` opens a missing project through the real startup command path and acknowledges its diagnostic while verifying that the container remains hidden until startup completes. `EditorProjectStartupVisibility` creates or reopens a real project through startup arguments and checks that the engine is configured before the final reveal; repeat it against the same output to exercise saved project state. The existing `EditorSplash/StartupAndQuit` test also asserts that a quit before completion never shows the container. Run these groups separately because each complete Editor lifecycle owns plugin registration.

Manual acceptance is still required on Windows, Linux, and macOS with real project/rendering plugins: cold and warm project opening, available multi-monitor arrangements, live movement/hot-plug between different scale factors, light/dark desktop themes, a slow plugin, a failed project or rendering process, native OS quit/close during startup, and taskbar/Dock behavior. Rendered image-scale tests do not substitute for those platform checks.

The Windows validation workspace can use the existing `XII_OUTPUT_DIRECTORY_DLL` CMake option to isolate binaries when a live engine or asset processor holds the normal output directory open. That is a local build choice, not a new repository option or deployment requirement.
